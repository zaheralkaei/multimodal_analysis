# Code audit — October 2026

Scope: every script in `scripts/`, plus the two committed dashboards in `reports/`.
Method: line-by-line read, then an end-to-end run on a synthetic 20 s video
(4 solid-colour shots of 5 s each: red, green, blue and a test pattern) so that
each shot's thumbnail could be checked against a known colour.

## TL;DR

The earlier audits (`AUDIT.md`, `AUDIT_R2.md`) checked that the outputs were
**consistent with each other**, e.g. caption vs emotion vs lighting. They did not
check that the outputs **describe the right shot**. They don't: with the default
2 fps extraction, every per-shot vision result and camera-motion result in the
committed dashboards comes from the wrong part of the video.

### Evidence for #1 (from the committed dashboards)

| Video | Shot | Shot time | Thumbnail used | That frame's time at 2 fps |
|---|---|---|---|---|
| `rtwpk9rb1Dc` | 70 | 208.2–213.1 s | `frame_00211` | 105.0 s |
| `rtwpk9rb1Dc` | 1 | 2.8–5.2 s | `frame_00005` | 2.0 s (previous shot) |
| `Z2ki180nHCI` | 32 | 121.2–125.6 s | `frame_00124` | 61.5 s |

The same mapping drives phase 3. Its frame range `int(start)+1 … int(end)+1` also
includes one frame past the shot end. So `shot_vision.csv`, `shot_camera.csv`,
`sync_per_shot.csv` and both `reports/*/dashboard.html` are invalid and must be
regenerated (phases 1→8). Phase 2's resume logic now discards the old rows
automatically, because their `mid_frame` no longer matches. Conclusions in
`docs/COMPARISON_1FPS_VS_2FPS.md` (the 2 fps camera-motion distribution) were
computed on misaligned frames and should be redone.

On the synthetic video, the fixed code picks mid-frames `00006/00016/00026/00036`
(red/green/blue/test pattern, all correct). The old formula would have given
`00003/00008/00013/00018`, and the last two are green, not blue or the test pattern.

## Not fixed: recommendations

Methodology (changes results, so the decision is yours):

- **CLAP softmax over 27 mixed tags** (`phase5_audio.py`). Mood, section and instrument
  prompts compete in one softmax, which flattens and couples the mood scores. This is a
  likely contributor to the "21/27 tags have ~0 variance" finding. Use a softmax per
  tag group, or raw cosine similarity.
- **Camera classifier thresholds** (`phase3_camera.py`). `static` only fires on
  median flow < 0.3 px, but `pan` has no minimum (`abs_pan > abs_tilt`). Small residual
  motion is therefore labelled pan, and `handheld` is reachable only when pan ≤ tilt ≤ 0.2.
  Subject motion is not separated from camera motion.
- **ContentDetector docstring** (`phase1_shots.py`) says it catches fades and dissolves.
  ContentDetector is a cut detector; gradual transitions need `AdaptiveDetector` or
  `ThresholdDetector`.
- **Emotion normaliser** (`_normalize_emotion.py`). `wistful` and `fierce` appear under
  two labels (the last one wins), and the substring fallback can match inside unrelated words.

Engineering:

- Dashboard always reports the vision model as `gemini-3-flash-preview`. Phase 2 never
  records the model it used, and the "Gemini 3 Flash" labels are hard-coded in the HTML.
- The mood tag list is copied in phases 5, 7 and 8. Import it from one place.
- `_test_*.py` still hard-code `C:\github_projects\…` paths.
- Phase 0 timeouts (120 s audio, 300 s frames) will fail on long videos.
- Phase 4 defaults to `small.en` but `run_pipeline.py` passes `small`. The docstrings disagree.
- Phase 5's `--device` flag is ignored.
- `requirements.txt` uses `>=` (not pinned, despite the comment). There are no automated
  tests or CI, and a small synthetic-video smoke test like the one above would have caught #1–#4.
- Committed dashboards reference `frames/*.jpg`, which `.gitignore` excludes, so thumbnails are broken on GitHub.
